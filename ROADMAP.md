# Дорожная карта

Работа: **разбор библиотеки** — устойчивость к плохому входу, ошибки расширений, буфер обмена,
подключение темы, экранный диктор, картинки, производительность. Пункты пришли из разбора всей
библиотеки; «п. N» — номер пункта в нём.

## Правила этапов

- Этап — один коммит с заголовком «Разбор библиотеки, этап N: <название>». Коммитит пользователь
  или агент с его разрешения.
- Ломать публичный API и ключи темы можно: пакетом никто не пользуется, Storaxis сидит на старой
  версии и переедет как на новый контрол.
- После этапа: `dotnet build Beresta.Markdown.Wpf.slnx` без предупреждений, `dotnet test
  Beresta.Markdown.Wpf.Tests` зелёный на всех платформах библиотеки, коммит; раздел этапа вырезается
  из дорожной карты, остальные не перенумеровываются. Скилл `keep-clean` — один раз, в самом конце.
- Правки вики — коммитом в сабмодуле `docs/wiki` (ветка `master`) с тем же заголовком, затем коммит
  основного репозитория с новым указателем сабмодуля. `sed -i` в Git Bash снимает CRLF — после него
  вернуть переводы строк.
- Новый или изменённый публичный член — XML-док по-английски и перевод в
  `Beresta.Markdown.Wpf/Docs/Beresta.Markdown.Wpf.ru.xml`; `DocumentationTests` это проверяют.
- Изменённое поведение — в вики на обоих языках, в `README.md` и `README.ru.md` — если они о нём
  говорят. Новый снимок вики — блоком в `tools/WikiShots.cs`.
- Новый ключ темы заводится, только если по смыслу не подходит ни один существующий; одинаковые по
  смыслу значения — одним ключом.
- Проверка вне тестов — пробой-потребителем в scratchpad: своё консольное WPF-приложение со ссылкой
  на проект библиотеки, окна за экраном, буфер обмена — только перехватом `DataObject.Copying` с
  отменой.
- Замеры производительности разрешены только в этапах 15 и 16 и только для п. 23–26.

## Известные факты

Проверено пробами и сборками при разборе — заново не вычислять.

- **Раскладка WPF падает с переполнением стека** (окно за экраном, главный поток) около 110 уровней
  цитат и 150 вложенных `<div align="center">`; разбор разворачивает не больше 32 контейнеров.
- **Markdig бросает `ArgumentException: Markdown elements in the input are too deeply nested`** на
  `>`×250 и `- `×120 (у списка два контейнера на уровень), на заголовке `#` с 5000 звёздочек вокруг
  текста (рисует заголовок для `AutoIdentifiers`) и на 100 000 `[` подряд. `>`×120 и 100 000
  звёздочек вокруг текста в абзаце, в ссылке, в ячейке таблицы он разбирает.
- **`ThemeInfo`** (проба с отдельной сборкой): стиль и шаблон темы применяются без слияния словаря, и
  чужой неявный стиль без `BasedOn` их не ломает. Строковые ключи (`DynamicResource Md.*`) WPF в
  словаре темы не ищет — только ключи-типы и `ComponentResourceKey`. Со словарём, влитым в ресурсы,
  ключи находятся.
- **Литералы оформления в `Themes/Generic.xaml`:** 10 цветов в 6 стилях, 31 размер и отступ в
  шаблонах, 8 начертаний. Запасные значения в коде (`MdTextBlock`, `MarkLook`, `MdLineGutter`)
  срабатывают только без темы.
- **XAML в документации:** объявления `clr-namespace:Beresta…` — в `README.md`, `README.ru.md` и на
  18 страницах вики на каждом языке; префиксы в примерах английских страниц — `mdv:` 136 раз,
  `kit:` 78, `p:` 10, `mdx:` 4, `s:` 4, на 29 страницах; русские страницы — так же.
- **Публичные типы:** 146, имена между пространствами имён не повторяются.
- **Платформы:** библиотека и тесты собираются под .NET 7, 8, 9 и 10; тестам под .NET 7 нужен
  `Microsoft.NET.Test.Sdk` 17.11 — новые версии .NET 7 не поддерживают. .NET 8 и .NET 9 теряют
  поддержку 10 ноября 2026, .NET 10 поддерживается до 14 ноября 2028.
- **Встроенная тёмная тема WPF** (`ThemeMode`, тема Fluent) есть в .NET 9 и 10, помечена
  экспериментальной (`WPF0001`).
- **Восстановление пакетов** в этом окружении для нового проекта идёт минутами: недоступный
  частный NuGet-источник даёт `NU1900`. Сборку под другую платформу делать на копии и ждать в фоне.

## Этап 8. Подключение темы: `ThemeInfo` и подсказка (п. 10)

**Зачем.** Свой неявный стиль вьюера без `BasedOn` молча даёт пустой вьюер; неподключённая тема —
тоже пустота без объяснений.

**Что сделать.**
1. Атрибуты сборки — новый файл `Beresta.Markdown.Wpf/AssemblyInfo.cs` (в этапе 10 туда же лягут
   `XmlnsDefinition`): `[assembly: ThemeInfo(ResourceDictionaryLocation.None,
   ResourceDictionaryLocation.SourceAssembly)]`. `Themes/Generic.xaml` остаётся одним словарём: для
   WPF это тема со стилями по типу (`MarkdownViewer`, `MdBlocksPresenter`, `MdBlockItem`,
   `MdLineGutter`), для потребителя — словарь ключей, который он вливает, как раньше. Адрес
   подключения не меняется.
2. Подсказка о неподключённой теме — в шаблоне вьюера скрытый `TextBlock x:Name="PART_ThemeHint"`.
   Его текст по-английски задан литералом: ключей в этот момент нет. В XAML — пометка `BYDESIGN`.
   Вьюер на первом `Loaded` проверяет `TryFindResource("Md.DefaultStyleProvider")`. Если ключа нет —
   показывает подсказку и пишет `Trace.TraceWarning` с адресом словаря.
3. Автоподключение словаря в ресурсы приложения не делаем.
4. `AGENTS.md` библиотеки, раздел «Тема»: «Стили по типу — стили темы (`ThemeInfo`): чужой неявный
   стиль их не заменяет. Строковые ключи `Md.*` WPF в теме не ищет — они доступны, только когда
   словарь влит в ресурсы».

**Тесты** — `ThemeTests`: свой неявный стиль `MarkdownViewer` без `BasedOn` в ресурсах окна — блоки
есть, `StyleProvider` не `null`. Случай «словарь не влит» тестами не проверить: `WpfHost` вливает
словарь в приложение глобально. Он проверяется пробой в отдельном процессе.

**Документация.** README на обоих языках и вики Getting-Started, оба языка: без словаря вьюер
показывает подсказку, а не остаётся пустым. Styles-and-Templates, оба: свой стиль вьюера больше не
обязан `BasedOn`.

## Этап 11. Склейка мягких переносов (п. 13)

**Зачем.** Абзацы, перенесённые в исходнике вручную, сейчас рвутся по строкам исходника, и переключить
это на поведение GitHub нельзя.

**Что сделать.**
1. Свойство вьюера — наследуемое прикреплённое, как `ShowCodeLineNumbers`: рабочее имя
   `JoinSoftLineBreaks`, `bool`, по умолчанию `false`. Смена значения — разбор заново, как у
   `BaseUri` (`Rebuild()`); фоновый разбор берёт значение на старте.
2. Разбор: параметр в `ModelBuilder` (через `Parse`). В `WalkInline` мягкий `LineBreakInline`
   (`IsHard == false`) при включённом режиме даёт кусок текста `" "` с начертанием места и позицией
   разрыва (`AddText(" ", state, output, node)`) вместо `LineBreakVm`. Текст карты и рисунка
   по-прежнему считает одна функция, `MdTextMap.TextOf`.
3. Последствия режима — описать, не чинить:
   - номера строк внутри абзаца встают по экранной строке начала строки исходника и могут сойтись на
     одной (`ScreenRows.WithoutOverlaps` оставит одну);
   - пустые места «панелей вровень» внутри абзаца встают на границу блока: `GapLayout.LocateInText`
     ищет `LineBreakVm`;
   - копирование в Markdown склеивает строки абзаца.

**Тесты.** `a\nb` в режиме — карта `a b`, в `MdTextBlock` один кусок без `LineBreak`; `a  \nb`
(жёсткий перенос) — перенос остаётся; `SourceLineOf` у позиции `b` — 1; разметка выделенного —
`a b`.

**Документация.** How-It-Renders, оба языка — абзац о склейке рядом с абзацем «каждая строка
исходника — новая строка»; Settings-and-Hooks, оба — строка; Line-Numbers и
Source-Lines-and-Two-Panes, оба — ограничения режима; перевод в ru.xml.

## Этап 12. Фоновый разбор и потоки (п. 14)

**Зачем.** С порогом фонового разбора резолверы и обработчики приложения вызываются из чужого
потока, и гонка с потоком интерфейса не даёт исключения.

**Что сделать.**
1. `MdExtension.AllowsBackgroundParse` — `public virtual bool`, по умолчанию `true`. У
   `MdExtensionSet` — `true`, только если разрешают все части.
2. Маркерный интерфейс `IMdBackgroundSafe` в пространстве `Extensions`: резолвер или обработчик
   приложения, который можно звать из фонового потока.
3. Kit:
   - `WikiLinks`, `WikiEmbeds`, `Mentions` разрешают, если `Resolver is null or IMdBackgroundSafe`;
   - `Shortcodes` запрещает, если в `Handlers` есть обработчик не из встроенных: встроенные делегаты
     запомнить при создании и сравнивать по ссылке;
   - `IssueLinks` (`Templates` — данные) и остальные разрешают;
   - наборы считают сами — через `MdExtensionSet`.
4. `MarkdownViewer.StartParse`: фоновый разбор — только если текст не короче порога **и** все
   активные расширения его разрешают; иначе разбор идёт в потоке интерфейса.

**Тесты** — `BackgroundParseTests`:
- расширение с `AllowsBackgroundParse = false` — `ConvertBlock` идёт в потоке интерфейса даже при
  тексте длиннее порога (поток запоминать в расширении);
- `WikiLinks` с простым резолвером — поток интерфейса, с резолвером `IMdBackgroundSafe` — фон;
- `Shortcodes` со своим обработчиком — поток интерфейса, только со встроенными — фон.

**Документация.** Live-Preview, оба языка, раздел «Long text in the background»; Extensions, оба —
свойство; Kit-Links и Kit-Media, оба — пометка резолвера и обработчиков; Settings-and-Hooks, оба;
перевод в ru.xml.

## Этап 13. Картинки: кэш, сеть, декодирование (п. 17)

**Что сделать.**
1. Публичный фасад кэша — статический класс (имя `MdImageCache` отдать ему, нынешний внутренний
   переименовать):
   - `Budget` — бюджет в байтах, сейчас 128 МБ;
   - `Clear()` и `Invalidate(…)` по адресу. Адрес — такой, каким его разрешил вьюер: ключ кэша сейчас
     `uri?.ToString() ?? image.Url`;
   - после `Clear` и `Invalidate` — внутреннее статическое событие. `MdImage` подписан на него, пока
     загружен (`Loaded`/`Unloaded`, без утечек), и перезапрашивает картинку, если адрес совпал.
     Событие может прийти из любого потока — дальше через `Dispatcher`.
2. `MdImageLoader`:
   - предел размера — статическое `MaxDownloadBytes`, 20 МБ по умолчанию:
     - `http(s)` — `HttpCompletionOption.ResponseHeadersRead`, проверка `Content-Length` и чтение
       потока со счётчиком;
     - файл — по `FileInfo.Length`;
     - `data:` — по длине base64;
     - превышение — `null`, то есть alt-текст;
   - заголовок `User-Agent: Beresta.Markdown.Wpf/<версия сборки>` в `DefaultRequestHeaders` общего
     `HttpClient`.
3. `IMdImageLoader.LoadAsync(string url, Uri? uri, int decodeWidth, CancellationToken)` — ширина
   декодирования в сигнатуре; ломающее изменение, принято. `MdImage.Load` считает `DecodeWidth` для
   любого загрузчика. Нынешний закрытый `Decode` — публичным помощником
   `MdImageLoader.Decode(byte[] bytes, int decodeWidth)` для своих загрузчиков.
4. Тестовые загрузчики — на новую сигнатуру: `AccessibilityTests.OnePixel`,
