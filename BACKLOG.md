## Пакет

- [x] **`dotnet pack` падает с NU5039.** `README.md` назначен страницей пакета (`PackageReadmeFile`
  в csproj библиотеки), но в сам пакет не включён: файл лежит в корне решения, а не в папке
  проекта. Нужен элемент `None` с `Pack="true"` и `PackagePath="\"` на `..\README.md`.
  Источник: проверка упаковки при знакомстве с проектом.
- [x] **Пакет не объявляет зависимость от Markdig.** В csproj библиотеки стоит
  `SuppressDependenciesWhenPacking`: при подключении сабмодулем это не мешает, а потребитель из
  NuGet Markdig не получит, и вьюер упадёт на первом разборе. Сначала выяснить, намеренно ли это.
  Источник: разбор csproj при знакомстве с проектом.
- [x] **README молчит о подключении темы.** Без `Themes/Generic.xaml` в ресурсах приложения
  (`pack://application:,,,/Beresta.Markdown.Wpf;component/Themes/Generic.xaml`, как в `App.xaml`
  демо) вьюер пуст: сборка библиотеки не объявляет `ThemeInfo`, и тема сама не подхватывается.
  Два пути: описать подключение в README либо объявить `ThemeInfo` в библиотеке — тогда
  подключение станет необязательным, а перекрытие ключей темы у потребителя продолжит работать.
  Источник: сверка README с демо при знакомстве с проектом.
- [ ] **Сборка под .NET Framework 4.8 и 4.7.2.** Пакет собирается только под современный .NET.
  Markdig 1.1.3 сборки под `net462` и `netstandard2.0` имеет, проект WPF в стиле
  SDK под `net48` и `net472` собирается, тесты — двумя платформами больше в
  `Beresta.Markdown.Wpf.Tests`: xUnit 2 и FluentAssertions 6 их поддерживают. Источник: разбор
  библиотеки, решение пользователя — отложено до потребителя на .NET Framework. Мешает код библиотеки:
  - члены интерфейсов с реализацией по умолчанию — их нет в среде .NET Framework, и заглушкой их не
    заменить: десять необязательных шаблонов `IMdStyleProvider` и оба метода `IMdLinkResolver`. Нужен
    другой контракт, например абстрактные базовые классы провайдера и резолвера, — а это меняет
    публичный API и для новых платформ;
  - `[GeneratedRegex]` — 21 место, генератор есть только в .NET 7+; под старые платформы —
    обычные `Regex` с `RegexOptions.Compiled`;
  - API, которых в .NET Framework нет: `ReferenceEqualityComparer` (11 мест), `Math.Clamp` (27),
    `TryAdd` и `GetValueOrDefault` у словарей (21), перегрузки строк с `char` у `StartsWith`,
    `Contains` и `Split` (десятки мест), `Task.IsCompletedSuccessfully`, `Environment.TickCount64`,
    `ArgumentOutOfRangeException.ThrowIfLessThan`, `File.ReadAllBytesAsync`,
    `HttpClient.GetByteArrayAsync` с токеном, `await using`; решается своими помощниками;
  - возможности языка, которым нужны типы BCL: записи и `init` (`IsExternalInit`), индексы и
    диапазоны `[^1]`, `[..]` (75 мест, `System.Index` и `System.Range`), `AsSpan` (пакет
    `System.Memory`) — заглушками, своими или пакетом вроде PolySharp. C# 14 на .NET Framework
    официально не поддерживается, но компилируется всё, кроме возможностей, которым нужна среда.
- [ ] **Сборка под .NET 6.** Проверено сборкой копии библиотеки; среда WPF 6 на машине установлена.
  Источник: разбор библиотеки, решение пользователя — отложено. Сверх того, что нужно для .NET 7,
  мешает:
  - 21 `[GeneratedRegex]` — генератор есть только в .NET 7+; под .NET 6 — обычные `Regex` с
    `RegexOptions.Compiled`, условной сборкой `#if NET7_0_OR_GREATER` или для всех платформ. Места:
    `ModelBuilder.HtmlSpaces`, `HtmlTag` (два), `HtmlToken`, `MdMarkdownWriter.OrderedMarker`; в Kit —
    `AdmonitionParser`, `CalloutContainers`, `CssColor` (два), `FrontMatterProperties` (три),
    `IssueLinks`, `ObsidianCallouts`, `ShortcodeParser` (два), `SpoilerParser`, `VideoSites` (два),
    `WikiLinkParser`, `WikiEmbeds`;
  - члены `required` в семи узлах Kit — `CriticInline`, `MentionInline`, `ShortcodeInline`,
    `SpoilerInline`, `TagInline`, `TaskStatusInline`, `WikiLinkInline`: в .NET 6 нет атрибутов
    `RequiredMemberAttribute` и `CompilerFeatureRequiredAttribute` — свои внутренние заглушки или
    без `required`.

## Ссылки

- [x] **Вынести открытие ссылок из вьюера.** Сделать отдельный способ перекрыть стандартное
  поведение ссылок, чтобы обрабатывать их снаружи контрола. Сейчас необработанную ссылку вьюер
  открывает сам (`MdTextBlock.OpenExternal`, только веб и почта); приложение может перехватить
  отдельное нажатие событием или командой, но не заменить поведение по умолчанию целиком.
  Источник: пожелание пользователя при разборе схемы рендера.
- [ ] **Ссылка из множества кусков рисуется минутами.** Каждый кусок текста внутри ссылки —
  отдельный `RunVm`, и `MdTextBlock.Dress` оборачивает каждый в свой `Hyperlink` с подсказкой и
  подпиской на `RequestNavigate`. Ссылка из 100 000 кусков — `[`, 100 000 раз `\*` и `](url)` —
  рисуется дольше 10 минут, тот же текст без ссылки — около 4 с, один кусок в 200 000 знаков в ссылке
  — 52 с; чужой текст так вешает интерфейс. Путь для множества кусков — один `Hyperlink` на ссылку с
  кусками внутри; для одного длинного куска сначала найти замером, куда уходит время. Нажатие,
  подсказка, выделение, копирование и узел автоматизации ссылки остаются прежними. Замер — только с
  разрешения пользователя. Источник: проверка устойчивости к плохому входу при разборе библиотеки —
  отложено.

## Направления

- [ ] **Готовый документ на вход.** Публичный разбор текста в модель и свойство вьюера
  `Document` рядом с `Markdown`. Сейчас не нужно: чат одним вьюером собирается склейкой сообщений
  в одну строку со своим контейнером-расширением, две панели работают со строками. Вернуться, если
  замер покажет, что разбор тормозит интерфейс, или появится чат, где склейка не годится. Замер
  делается только с разрешения пользователя, самостоятельно его не запускать. Цена:
  документ из нескольких текстов ломает позицию в исходнике (номера строк, две панели,
  копирование в markdown, редактирование), два входа требуют правил старшинства, расширения
  разбора и вьюера могут разойтись. Источник: разбор точек расширения с пользователем —
  отложено.
- [ ] **Редактирование: правка блока с фокусом.** Выбранный путь: блок под курсором показывает
  поле ввода со своим куском markdown, остальные остаются отображением; после правки кусок
  вклеивается в исходник, документ пересобирается инкрементально. Весь документ в полях ввода не
  годится: каждое поле держит своё выделение, и сквозное выделение пропадает. Отдельный редактор
  сырого markdown остаётся потребителю запасным путём. Опирается на этапы 1, 2 и 5
  [`ROADMAP.md`](ROADMAP.md): позиции в исходнике, карту с соответствием исходнику,
  инкрементальную пересборку. Трудные места: правка поперёк выделения, переход курсора между
  блоками, отмена, блок, поглощающий соседей (открытое ограждение кода). Начинать с блока верхнего
  уровня. Источник: решение пользователя при обсуждении архитектуры — отложено.
- [ ] **Подсветка синтаксиса в блоках кода.** Язык из строки информации уже доходит до
  презентера (`CodeBlockPresenter.Syntax`), но не используется. Источник: пожелание пользователя.
- [ ] **Гибрид для блоков кода: текст на `TextFormatter`.** Блок кода остаётся элементом со своим
  шаблоном, а код внутри рисует свой элемент на `TextFormatter` вместо `MdTextBlock`: раскладываются и
  рисуются только видимые строки. Сейчас виртуализация идёт по блокам, и блок кода на десятки тысяч
  строк раскладывается целиком, как только виден его край. Строчных виджетов в коде нет, поэтому
  трудное место гибрида — живые контролы внутри текста — здесь не встаёт. Остаются своё попадание
  мышью, выделение, координаты кусков текста для `GetRangeRects`, номера строк в коде и DPI.
  Решать по замеру: длинный блок кода, быстрая прокрутка, потоковый ответ с кодом; замер — только с
  разрешения пользователя. Источник: разбор подходов к рисованию с пользователем — отложено.
- [ ] **Большие таблицы.** Документ виртуализируется по блокам, а таблица — один блок:
  `MdTablePresenter` создаёт все ячейки сразу в одной сетке `Grid` и при каждой перераскладке с той же
  шириной заново меряет каждую ячейку при бесконечной ширине (`MeasureColumns`), чтобы подобрать ширины
  столбцов. Таблица на тысячи строк — CSV через `CsvTables`, отчёт, ответ модели — даёт десятки тысяч
  элементов. Путь: сначала кэшировать естественную и наименьшую ширину ячеек и перемерять только
  изменившиеся; с порога — виртуализировать строки: ширины столбцов подбирать по выборке строк
  (первые N и видимые), строки класть в виртуализирующую панель по образцу `MdBlockPanel`. Решать по
  замеру: таблицы на 500, 2000 и 10 000 строк; замер — только с разрешения пользователя. Источник:
  разбор библиотеки — отложено.
- [ ] **Стандартная тёмная тема WPF — проверить в апреле 2027.** С .NET 9 в WPF есть встроенная тема
  Fluent: `ThemeMode="Dark"` на приложении или окне; в .NET 9 и .NET 10 этот API помечен
  экспериментальным (`WPF0001`). Тема вьюера рассчитана на стандартную светлую тему: шапка таблицы и
  ключи карточки свойств — непрозрачный `#DFDFDF` (`Md.Table.HeaderBackground`) под цветом текста
  приложения, и при `ThemeMode="Dark"` на нём белый текст. Когда `ThemeMode` станет стабильным, решить,
  подстраивать ли тему вьюера под него. Источник: разбор библиотеки, решение пользователя — отложено
  до стабилизации.
- [ ] **Анимация GIF.** Картинку декодирует `BitmapImage` в `MdImageLoader`, и WPF показывает у GIF
  только первый кадр. Нужен показ кадров в `MdImage` — кадры из `GifBitmapDecoder`, смена по задержкам
  из метаданных кадров — и кэш, который держит все кадры и учитывает их в бюджете памяти. SVG —
  отдельная идея, `docs/ideas/svg-images.md`. Источник: разбор библиотеки — отложено.
